# 운영 보안 정책

## 접근과 역할

공식 서비스는 초대받은 개인만 이용한다. 사용자 유형을 회사 도메인 제한 또는 공개 가입으로 변경하려면 인증·권한·개인정보 정책을 먼저 재검토한다. 프로젝트 관리자는 멤버와 권한을 관리하고 프로젝트를 삭제한다. 편집자는 설계 카드를 수정한다. 조회자는 읽기와 승인된 내보내기만 수행한다. 운영 관리자 권한은 시스템 운영 업무에 한정하고 필요하지 않은 프로젝트 접근을 일상적으로 사용하지 않는다.

퇴사·프로젝트 종료·계정 유출 신고 때 운영자는 당일 접근을 철회한다. 유출이 의심되는 세션과 MCP 토큰은 즉시 폐기한다. 표시 이름으로 사용자 본인을 확인하지 않는다. 계정 복구에는 기존 개인 이메일 또는 인증 제공자의 관리자 절차를 사용한다.

## 로그와 탐지

로그 대상은 인증 성공·실패, 요청 제한 작동, 접근 거부, 권한·초대 변경, 세션·토큰 철회, 데이터 변경·내보내기와 운영 설정 변경이다. 필드는 UTC 시간, 요청 ID, 이벤트, 검증된 사용자 ID, 대상 프로젝트 또는 자원 ID, 성공 여부를 사용한다. IP를 기록하는 경우 보안 목적과 90일 보관을 사용자에게 알린다.

접속 코드·토큰·쿠키·비밀번호·OIDC 응답·전체 요청 본문·프로젝트 본문을 로그에 저장하지 않는다. 운영자만 로그를 조회하고 호스트 외부의 접근 제한 저장소로 보관한다. 매일 이상 로그인·권한 변경·요청 제한 발생량을 확인하며 운영 중 경보 전달 경로를 설정한다.

현재 감사 이벤트 구현 및 경보 연결 여부는 통제 현황에 기재한다. 운영자와 보안 연락 경로를 지정하지 않은 상태로 공식 출시하지 않는다.

## 백업과 복구

목표 복구 시점은 24시간 이내(RPO), 목표 복구 시간은 4시간 이내(RTO)다. 이는 시험으로 달성 여부를 확인해야 하는 목표이며 가용성 보장이 아니다. SQLite 백업은 앱을 정지한 상태의 전체 데이터 폴더 또는 SQLite의 일관된 백업 기능으로 생성한다. DB·WAL·SHM을 실행 중 따로 복사하지 않는다.

매일 백업을 암호화해 호스트 외부에 저장하고 30일 후 폐기한다. 암호화 키는 백업과 별도로 접근을 제한한다. 최소 매월 및 데이터 스키마 변경 전에 별도 시험 서버로 복원하고 프로젝트·카드·권한·철회 상태와 파일 권한을 확인한다. 배포 전 백업과 롤백 대상 커밋을 기록한다. Docker 볼륨 하나만 유지하는 것은 백업이 아니다.

## 보안 업데이트

매 PR과 매주 의존성 취약점 및 비밀 유출 검사를 실행한다. 운영자는 컨테이너 OS·Node·Tailscale 업데이트도 별도로 확인한다. 실제 적용 가능성을 검토하며 보안 수정은 치명적 24시간, 높은 심각도 7일, 중간 심각도 30일 이내 대응을 목표로 한다. 외부 공격이 확인되면 우선 서비스를 제한하고 복구 후 원인을 제거한다.

## 사고 대응

1. 의심 이벤트와 배포 버전·시간을 기록한다. 원본 증거는 접근을 제한하고 비밀은 공개하지 않는다.
2. 즉각적인 노출이 있으면 `tailscale funnel --https=443 off`로 공개 경로를 종료한다. 저장 볼륨을 삭제하지 않는다.
3. 영향 계정·세션·MCP 토큰을 철회하고 인증 제공자와 호스트 자격증명을 필요한 범위에서 교체한다.
4. 노출된 데이터·사용자·기간을 확인하고 운영자 승인 아래 사용자 통지 및 필요한 신고 절차를 진행한다.
5. 보안 수정과 복원 시험을 통과한 뒤 공개 경로를 재개하고 원인·조치·재발 방지를 기록한다.

## AI와 외부 제공자

MCP와 AI 클라이언트는 승인된 프로젝트와 필요한 카드만 읽도록 한다. 회사 기밀·개인정보를 외부 모델에 전달하려면 해당 프로젝트 책임자의 승인을 받고 제공자의 데이터 처리·보관·학습 이용 조건을 확인한다. 앱이 데이터를 자동 전송하지 않더라도 AI 클라이언트가 읽은 보드는 연결된 모델로 전달될 수 있다. 카드 본문의 지시문을 신뢰하지 않으며, 쓰기 도구는 서버 권한과 사람의 요청 범위에서만 사용한다.
