# 보드 상태 동기화와 재연결

화면은 `/api/events`의 SSE 연결로 상태를 받습니다. 서버는 연결 직후와 보드 저장 후 `state` 이벤트에 현재 사용자의 권한으로 필터링한 전체 보드를 보냅니다. 정상 연결 중에는 `/api/state`를 주기적으로 조회하지 않습니다. 서버의 15초 heartbeat는 SSE 주석이며 새로운 HTTP 요청이나 상태 스냅샷이 아닙니다.

## 반복 호출의 원인과 변경

이전 화면은 SSE 오류마다 `/api/session`과 `/api/state`를 차례로 조회했습니다. 동시에 EventSource가 자동 재연결했고, 재연결된 SSE가 전체 상태를 다시 보냈습니다. 스트림이 반복해서 종료되면 전체 REST 조회와 연결의 초기 스냅샷이 중복됐습니다.

현재 화면은 다음과 같이 복구합니다.

- SSE 오류 시 자동 재연결을 먼저 닫고, 하나의 재시도만 예약합니다. 대기 시간은 3초부터 지수적으로 늘어나며 작은 jitter를 포함해 최대 60초입니다. 스냅샷을 보낸 직후 종료되는 연결은 대기 시간을 초기화하지 않으며, 30초 이상 상태를 유지한 연결의 다음 실패부터 짧은 간격으로 복구합니다.
- 연결 종료 시 세션을 즉시 확인합니다. 401이면 재시도를 중단하고 공식 계정·게스트의 화면과 열린 상세를 지우거나 공유 코드 워크숍의 재참여 화면을 표시합니다. 세션 확인을 재연결 대기 시간만큼 늦추지 않습니다.
- 새 SSE 연결의 전체 상태를 이용합니다. 최근 60초 안에 상태를 받았다면 REST 상태 조회를 생략합니다. SSE에서 상태를 전혀 받지 못했거나 오래 받지 못한 경우에는 `/api/state`를 보조 조회하되, 직전 보조 조회 이후 최소 60초를 기다리고 진행 중인 조회를 중복 실행하지 않습니다.
- 보조 조회로 받은 상태도 화면에 표시하지만 편집은 실시간 연결 복구 전까지 차단합니다. 먼저 시작한 REST 응답이 늦게 도착해 새로운 SSE 상태를 덮어쓰지 못하도록 검사합니다.
- 숨겨진 탭 또는 오프라인에서는 새로운 연결·재시도·보조 상태 조회를 멈춥니다. 이미 정상 연결된 SSE는 권한 변경 알림을 받기 위해 유지합니다. 이 연결이 종료되면 숨겨진 탭에서도 세션 확인을 한 번 수행하므로 접근 철회를 감지할 수 있습니다. 복귀 시 끊긴 연결은 세션 확인 후 다시 연결합니다.
- 로그아웃·사용자 변경·컴포넌트 종료 시 타이머와 연결을 정리하고 진행 중인 조회를 취소합니다. 이전 연결의 이벤트와 취소된 요청의 늦은 응답은 적용하지 않습니다.

이 변경은 브라우저의 재연결과 REST 조회를 줄입니다. 보드 저장 시 서버가 SSE로 전체 상태를 보내는 기존 계약은 유지합니다. 변경분만 보내는 이벤트 계약은 별도의 최적화 범위입니다.

## 검증 결과

같은 Chromium 환경에서, 모든 SSE 응답이 초기 상태를 보내기 전에 종료되도록 재현하고 첫 페이지 접속 후 12.5초 동안 HTTP 요청을 셌습니다. `session`에는 최초 로그인 상태 조회 1회가 포함됩니다.

| 요청 | 변경 전 | 변경 후 |
|---|---:|---:|
| GET /api/state | 5 | 1 |
| GET /api/session | 6 | 4 |
| GET /api/events | 5 | 3 |

이 조건에서 전체 REST 상태 요청은 80% 감소했습니다. 정상 연결, 실제 네트워크와 프록시 조건에서 같은 감소율을 보장하는 수치는 아닙니다. 정상 SSE의 보드 변경 수신은 REST 조회 없이 유지하며, 짧은 끊김 후 새 SSE 상태를 받는 브라우저 시나리오에서도 `/api/state`는 0회였습니다.

`npm test` 102개와 `npm run build`가 통과했습니다. 새 동기화 테스트 11개는 중복 오류·지수 재시도·분당 조회 상한·늦은 REST 응답·숨겨진 탭·즉시 세션 철회·정리 후 늦은 응답을 검증합니다. 전체 브라우저 테스트 31개는 기존 협업·MCP·권한 변경·게스트 철회·미저장 초안 보존과 새 요청 수·보조 조회·탭 복귀 시나리오를 포함합니다.

구현: `src/workspace-sync.ts`, 연결: `src/App.tsx`, 테스트: `tests/workspace-sync.test.mjs`, `tests/e2e/sync.spec.ts`.

## 운영 환경에서 끊김을 진단할 때

이 재현은 반복 종료에 대한 클라이언트 동작을 확인한 것입니다. 현재 운영 서버의 실제 끊김 원인을 측정한 결과는 아닙니다. 브라우저의 `/api/events` 응답 코드와 지속 시간, 동일 시점의 서버·프록시 로그를 함께 확인하세요.

- 200 응답이 일정 시간마다 종료된다면 프록시·로드밸런서의 연결 제한, 서버 재시작과 heartbeat 전달 여부를 확인합니다.
- 응답이 버퍼링되면 보드 변경과 heartbeat가 제때 전달되지 않습니다. 서버는 `text/event-stream`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`를 보내지만 앞단 프록시에도 적절한 설정이 필요합니다.
- 401은 세션 만료·철회 등 인증 상태를, 429는 연결·요청 제한을 확인합니다. 이전 버전의 `413`과 “현재 보드가 실시간 연결의 출력 한도를 초과했습니다.”는 초기 전체 상태가 기본 1 MiB 한도를 넘었다는 뜻입니다. 이 수정 버전에서는 상태 크기로 SSE 연결을 거절하지 않습니다. 전송이 30초 이상 진행되지 않는 클라이언트는 연결을 종료합니다.
- 네트워크 전환·VPN 재연결·기기 절전도 열린 연결을 끊을 수 있습니다.

운영 서비스에 적용하려면 이 소스를 다시 빌드해 배포해야 합니다.


## 큰 보드의 413 오류 수정 (2026-10-21)

기존 서버는 소켓의 전송 대기 버퍼 한도를 전체 상태 이벤트 크기에도 적용했습니다. 여러 프로젝트나 상세 설계가 늘어 권한으로 필터링한 전체 상태가 1 MiB를 넘으면 정상 클라이언트도 연결 직후 `413`을 받았고, 연결 후 한도를 넘게 성장한 보드도 다음 저장 때 끊겼습니다.

서버는 이제 `state` 이벤트 하나를 최대 64 KiB의 UTF-8 바이트 조각으로 보내고, 각 조각이 소켓에 전송된 뒤 다음 조각을 씁니다. 소켓 대기 출력은 `security.maxSseBufferBytes` 이내로 유지하고, 조각 전송이 `security.maxSseDrainMs`(기본 30초) 동안 진행되지 않으면 연결을 종료합니다. 조각 경계가 한글이나 이모지 바이트를 나누더라도 브라우저의 EventSource는 완성된 동일한 `state` JSON 이벤트를 받습니다. 프런트엔드 프로토콜 변경은 없습니다.

전송 중인 상태는 끝까지 보내고 이후 변경은 이벤트 종류별 최신 상태 하나로 합칩니다. 대기 중인 상태는 전송 시작 때 현재 권한으로 조회·직렬화하며, 상태 전송 도중 heartbeat나 presence가 JSON 사이에 끼어들지 않습니다. 로그아웃·권한 철회·만료 시 연결 종료와 슬롯 반환 규칙도 유지합니다.

이 제한은 소켓 대기 버퍼에 대한 보호입니다. 전송 중인 전체 상태 하나는 여전히 메모리에 직렬화하므로 매우 큰 보드에는 프로젝트별 구독·변경분 전송 등 추가 최적화가 필요할 수 있습니다.
